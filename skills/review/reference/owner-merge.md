# review — owner override, extra round and the merge hand-off

Read by the `review` skill (`skills/review/SKILL.md`) at the points it names: Owner override and Extra round (section 2, step 6) and 3.3 (the hand-off).

## Owner override (rare; only with `owner_approval: chat` in `P config`)

Only for an owner who says they want to dismiss what Claude or Codex would not (an item Claude or Codex's second review made ACCEPT): never offer or ask for it. By default you decide
(`P triage claude-ruling`, SKILL.md Rulings). This path is the only one that loosens an ACCEPT or clears an item Claude may not rule on.
Run `P triage ruling-request --pr N --ids R1-B1,R2-S3`. Your reply says "answer with only `<id>: accept | follow-up | reject`; reasons in another
message" and **ends with the exact `line` it printed**, nothing after it. The owner-go hook records the owner's next prompt against that line. Per
item: `P triage owner-ruling --round R --id ID --decision ACCEPT|FOLLOW-UP|REJECT --reason "<why>" --owner-quote "<the owner's whole answer, copied, never paraphrased>" --pr N`.
A background notice or another session's message between your ask and the owner's answer does not break a pending ruling (the answer binds across them) only while you answer it with tool calls alone: any text in your reply to such a turn voids the pending ask whatever it says (nothing is recorded, ask again), so keep a reply to a notice to tool calls; if you did write text, the owner's answer is refused with a nudge and you show the ask again in your reply to that prompt. One exception (#189): a reply to a task notice or a subagent hand-back that ENDS with the ruling line, with no tool call after it, is itself the pending ask (as if the owner had started that turn); an answer the owner queued while you were busy is refused for such an ask ⇒ ask again. A context compaction between the ask and the answer no longer loses it. A merge request does break (any later reply makes it stale): show it again. An answer the hook could not confirm as typed by the owner is refused (`provenance`) ⇒ ask again.
A refusal (changed finding text, wrong id, other words, label mode) ⇒ ask again with a fresh `ruling-request`. Then re-post `P comment --pr N --kind triage`,
`P followups create --round R`, and the comment again; an ACCEPT is built, `mark-implemented`, and reviewed in a new round. In label mode, `needsHuman`
items end in `needs-human` (as in step 6): the owner rules outside this session.

## Extra round

**Extra round** (only with `owner_approval: chat`; the owner's `extra round` is the only thing that lifts `review.max_rounds`). When `P state outcome` says
`reachedMax: true` with no `extraRound` and no `grantedRound`: commit and push the fixes and get `verify.quick` green (the grant names the head to be
reviewed), then run `P triage round-request --pr N`. It prints `{line, k, n, head}`; keep `n`. Your reply says in one plain-English paragraph what is
still open and what the extra round will review, and **ends with the exact `line`**, nothing after it. Then wait. When the owner types `extra round`
the owner-go hook records it against that line and prints a context line; only then run
`P codex-review --pr N --round <n from round-request> …` as in step 1 (it claims the grant after Codex answers; the output shows `grantUsed`). One grant is one
round: if that round accepts items again, ask again or park. A refusal that says the grant "cannot be confirmed as typed by the owner" (#128: the prompt was a harness message, or its transcript entry is gone or elsewhere; #191: or the owner typed it while you were still working, which the hook's one-line note also says) is a refusal too: `round-request` again, show its FRESH closing lines (the same for a "merge": re-run the dry run; for a ruling: `ruling-request`), and the owner types `extra round` themselves after the reply ends. A refusal (`round-cap` "ask again", grant already used, head moved) ⇒ run `round-request` again. Never
type, paraphrase or forge the owner's words, and never run Codex outside `codex-review`. Label mode ⇒ no grant exists: park as before. `review-complete` and the
final gate re-prove the grant from the owner's record on this machine, so finish the review here.

## 3.3 Endings: the merge hand-off

Which ending depends on the item note from 1.5 (as refreshed in step 2):

   - **A `blocking` item** (a blocking hard-stop or test-integrity violation: always under `owner_approval: label`) : NO `Head …` / `🔀` lines
     (`P merge --owner-go` refuses such a diff) and no `needs-human` label. Say the PR is reviewed and CI is green, name what blocks it
     (from `.review/hardstops.json` and `P integrity`), and give the repo's `merge.command` from `P config` with `{pr}` = N and `{sha}` = the head sha
     filled in (EagleWatch: `npm run merge -- <PR> --expect-head <sha>`) for the owner to run.
   - **Protected areas under `owner_approval: chat`** (`ownerMerge` items, nothing blocking): the owner's "merge" covers them. Run
     `P merge --pr N --dry-run --owner-go`; for a `say-merge` with `areas`, name the protected areas in plain English from its `areaIds` (never from the
     agent-writable `.review/hardstops.json`) and end the reply with the closing lines (last bullet). A dry run with blockers ⇒ fix them first; `owner-runs` ⇒ the first bullet.
     `ownerStep.behindNote` (behind main, accepted: base config `merge.behind_base: disjoint`) ⇒ say it in plain English ABOVE the Rulings block when present (else above the closing lines: Areas / Hold / Head), never between the block and the closing lines or between the closing lines: a prose line there voids the binding of the Rulings rows; "merge" still covers only that head and items.
   - **Rulings** (`ownerStep.rulings` present: dismissed BLOCKING or security items, single-PR requests only; several PRs with rulings ⇒ a separate reply for each): in plain English, above the closing lines, say what was dismissed and why, naming each item;
     then print the `Rulings <digest12>` block verbatim from the dry run, directly above `Areas` / `Hold` / `Head`. Never type or edit the block: that makes the "merge" bind nothing.
   - **A `needs-human` hold** (`ownerStep.hold` present, with or without areas): say in plain English that the owner's "merge" also lifts the needs-human hold; report it from the event, `ownerStep.holdInfo` (who added the label, when: the account is shared, so never call it the owner's or yours);
     quote `ownerStep.parkNote.text` only when `parkNote` is present, labelled `pipeline park note (agent-written)`, never as the hold's reason. Never start a prose line with `Hold <x> by`: a Hold-looking line outside the closing lines voids the request.
   - **Merge as a job.** The owner says "merge" ⇒ `P job start merge -- node ~/.claude/pipeline/bin/pipeline.mjs merge --pr N --owner-go`, then `P job wait merge --run-id <runId> --timeout 540` until `state` is `done` (it can outlast the Bash tool's 10-minute cap; `replaced`/`lost` ⇒ dry run and `gh pr view` first). Read `exitCode` and `tail`:
     `merged: true` ⇒ done (`holdLifted` names the lifted hold). `error: hold-recovery` with `prMerged: true` ⇒ the PR DID merge (an earlier run's auto-merge fired while recovery disarmed it): report it merged, read the merge commit with `gh pr view N --json mergeCommit`, make no new request. Output with `holdRestored`, `holdKept`, `holdRestoreUnverified`, `holdRemovedByOther`, any other `error: hold-recovery`, or `merge-in-progress` (another P merge of the PR is running, or an earlier run's merge command is still running after that run died; wait and run the dry run again), or `error: lock-timeout` with `reviewLockBusy` (a review writer holds this PR's review lock: wait for it to finish, then run the dry run again) ⇒ nothing merged: tell the owner plainly, show the NEW dry-run lines; `autoMergeDisarmFailed` ⇒ the owner disables auto-merge by hand; a restored hold is a new hold, so the owner must say "merge" again; after `merge-in-progress` or `lock-timeout` the new dry run can change the closing lines, so the owner's earlier "merge" is spent and a fresh "merge" is needed after the new lines.
     `holdRestoreFailed` (`error: hold-restore`) ⇒ the owner re-adds the label by hand; "PR comments unreadable" ⇒ run again later. A changed digest, areas or hold ⇒ show the new lines.
   - **Queue mode** (dry run `queue: true`; only when GitHub reports a merge queue on the base branch; queue off ⇒ everything above as today). One "merge" enqueues the approved head and GitHub merges it after testing it on top of main and everything ahead of it. No `P update-branch` for "behind" (except the `queue-branch-predates-switch` remedy below), no merge hold, no `Hold` line from a merge hold (a `needs-human` hold is still lifted by the "merge", as above). `ownerStep.queueNote` ⇒ say it in plain English where `behindNote` goes (above the Rulings block / closing lines, never between them). A `queueState` blocker ("already queued at position N" / "already merged") ⇒ report it and make no request. The merge job's output adds `queue, queued, requeued, position, stillQueued, removal`:
     `merged: true` ⇒ as today. `error: queue-removed` (`removal` has the reason and the failing check) ⇒ treat it like red CI: tell the owner, fix → new head → new review and request (after a second removal the owner may re-queue the SAME head with a fresh "merge", e.g. a flake; report it as red CI first). `error: queue-branch-predates-switch` (also the dry run's blocker of that kind, so no request is made; it carries `branchState`) ⇒ the branch's own merge script may not know the queue (it could take "queued" for "merged" and delete the branch): nothing was queued or run. Read `branchState`. `branchState: predates` = the PR's branch does not contain the commit the base names in `.claude/merge-queue-aware` (the commit that taught the repo's merge script the queue): run `P update-branch --pr N` from the PR's own worktree (it catches a predating branch up even in queue mode: `queueCatchUp: true`), `git pull --ff-only`, re-verify, run a review round (base-only), `P review-complete`, then ask the owner again (new head, new request). `branchState: unknown` = the BASE's marker is the problem (no file, not a full sha, a sha GitHub does not know, or a sha the base itself does not contain): an update cannot help (`P update-branch` answers `queue-mode`, no PUT), so run no update-branch and no review round: tell the owner the base's `.claude/merge-queue-aware` must be added or fixed (the full sha of the commit as it landed on the base), then run the dry run again. A `queue-sweep` re-queue of such a branch ends the record the same way (hold put back, owner told): same split. A failed read (a GitHub error on the marker or the ancestry; a head GitHub does not have, i.e. not pushed yet, counts too) is not a verdict on any path: it answers `queue-unreadable` (the dry run's blocker has that kind, a live record and its hold are kept, the sweep leaves it unsettled), so retry later (push the head first when the detail says it is not on GitHub); no update-branch, no review round. `error: blocked` ⇒ report the stop condition from `problems` (`needs-human` / `pipeline-blocked` label, open `pipeline-pause` / `pipeline-rollback` issue): the PR was dequeued. `queue-unreadable` / `enqueue-failed` ⇒ nothing is queued: say so, show the lines, retry later. `queued-elsewhere` ⇒ another checkout already queued it and the queue sweep carries it on: nothing to do. `requeue-due` ⇒ the live queue record is for ANOTHER head (a different worktree queued it) and its one automatic re-queue is due there. `P merge` never sweeps its own PR, so run `P queue-sweep` right away (do not wait for the scheduled sweep, which only exists on a machine with the LaunchAgent): it re-queues the record from that worktree, or ends it (worktree gone or at another head, hold put back). Report the sweep's outcome for this PR (`requeued`, or `ended` with its terminal; `queuedHead` / `recordRoot` name the record); an `ended` `removed` is red CI. A `queue-removed` that already says the worktree that queued it cannot re-queue it (it is this one, gone, or at another head) needs no sweep: treat it as red CI. A `head-moved` with `adopted` (the PR is in the merge queue at a head nobody approved: the hold is back, the record now tracks that entry and `queue-sweep` keeps it, never merging it on the old approval) ⇒ tell the owner the new head is queued unreviewed and needs a review round or a dequeue by hand. A `head-moved` that says the live queue record here is for another approval changed nothing: run `P queue-sweep`, then `P merge` again.
     `stillQueued: true` ⇒ tell the owner "queued at position N, GitHub merges it" (no new owner step), then relaunch the same `P merge --pr N --owner-go` job: it reconciles (never a second enqueue, never a dequeue, no new "merge") until it ends merged / removed / blocked. After 24 h in the queue, report it to the owner and keep waiting. If the session ends, `P queue-sweep` (a LaunchAgent every 10 min) carries the entry on and notifies the owner.
     One gap stays: a stop condition set after the queue's last check ended but before GitHub merges the group is caught only by the merge job's 90-second poll while a job runs; with no job running the sweep reports the PR as merged under veto after the fact.
   - Any owner command that starts with `gh` is written with gh's absolute path, shell-quoted (`/opt/homebrew/bin/gh …` on this kind of Mac, else `/usr/local/bin/gh`; `command -v gh` when it answers): the owner's `!` prompt shell does not load the PATH that has gh.
   - To preview the verdict before the owner's word, use only `P merge --pr N --dry-run` (add `--owner-go` for that route): same checks, writes and merges nothing; its `ownerStep` says which ending above applies.
     Read the dry run's WHOLE output (or the whole `ownerStep` object). Never pick single keys with `grep`, `--jq`, `jq` or a script, e.g. only `.line`: a filtered read silently drops `ownerStep.rulings`, `areas`, `hold`, `ready` or `behindNote`. A request missing one of them binds nothing, and the owner's "merge" is spent (EagleWatch #1702, 2026-11-06).
     Never run the repo's own merge command (`npm run merge …`, even with `--dry-run`) to preview: the git guard refuses it, and the dry run grants nothing.
   - **Merge hold** (only with `merge.hold_command` in `P config`). Run the dry run of this route first (`P merge --pr N --dry-run`, plus `--owner-go` only on that route); only when `ownerStep.holdEligible` is `true` (code-computed: no blockers beyond the owner-items check that makes it `owner-runs`; `wouldMerge` may be false then) run `P merge-hold --pr N` and add ONE plain-English line above the Rulings block when present (else before the ending) (hold confirmed, other merges pause up to 90 min); the ending stays LAST, unchanged. NOT confirmed (another PR may have taken its hold in between, #181) ⇒ run `P merge-hold --pr N --check` first: `queued-behind` ⇒ the merge-hold blocker ending below (name #A and its expiry, NO `Head` / `🔀` lines, stop: a "merge" there would only be refused and spent); clear ⇒ say in that one line that the hold is NOT confirmed and continue to the ending; `hold-unreadable` ⇒ as below. A `merge-hold` blocker in the dry run: name #A and its expiry (PHT), NO `Head` / `🔀` lines, stop. `hold-unreadable` anywhere: retry once after 60 s, then tell the owner and stop. Leaving the hand-off for PR N: `P merge-hold --pr N --release --reason <new-commits|parked|owner-declined|handoff-withdrawn|ci-failed|update-conflict|queued-behind|hold-unreadable>` (a merge needs no release). `new-commits` keeps the hold when the PR head is a catch-up the pipeline itself made (`P update-branch` / `P merge`; output `kept: own-successor`): run it on every push, it decides. `P merge` takes this PR's hold right before its own catch-up of a stale branch (output `hold`) and keeps it through the refusal that asks for re-verification; a conflicting catch-up (`rebase-needed`) releases it (`update-conflict`, `holdRelease`; not `confirmed` ⇒ run that release once yourself). `P merge` returns `queued-behind` (a hold it took in that run is already released: `holdRelease`): tell the owner which PR is ahead (`blockedBy`) and its expiry (PHT), do NOT `P update-branch`, offer the exits (say "merge" again after #A merges or expires; merge #A; the repo's own release / `--ignore-hold`, the owner's call), stop. A "merge" given before that refusal is never reused: on the next prompt re-run the dry run, show the new lines, run `P merge --owner-go` only on a "merge" after them. Never release, take or ignore a merge hold of any PR but N; never use `--ignore-hold`.
   - **No such item**, and the closing lines of every request: the reply's LAST lines are exactly (sha12 = first 12 characters of `git rev-parse HEAD`; owner/name from `gh repo view --json nameWithOwner`; on `--owner-go` copy
     them from the dry run, never type the digest: `ownerStep.rulings` when present, then `ownerStep.areas` and `ownerStep.hold` when present, then `ownerStep.line`, then `ownerStep.ready` when present, with nothing after; for a `say-merge` the dry run's `ownerStep.closing` is exactly these lines, so end the reply with it pasted verbatim, nothing before it on those lines and nothing after it):
     `Head <sha12> · items <digest> · repo <owner/name>`
     `🔀 Ready to merge #N — say "merge"`
     The owner-go hook binds the owner's "merge" to the LAST reply: if anything else was said since, or the context was compacted, show the lines again (a blank line between them is harmless, prose is not). Never type or simulate the owner's "merge".
     No record ⇒ `P merge` says so: show the request again and wait; but after a Hold line, with an installed pipeline that predates hold support (`pipeline update --check` shows it behind main), say "run pipeline update first" instead.
     A refusal that the transcript is not under a trusted config dir: the owner's Claude Code config dir must be a `.claude*` folder directly under the home (`CLAUDE_CONFIG_DIR` does not count): tell the owner. Label mode and the gated route are unchanged (the gated route lifts no hold).
